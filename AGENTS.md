# AGENTS.md

Agents-Driven Flow: build marketing audiences from customer data and sync them to a mock ad platform. TypeScript monorepo: React web app, GraphQL, NodeJS. Package manager: pnpm.

## Commands

Run from the repo root.
- First-time setup: `cp .env.example .env && pnpm install && docker compose up -d && pnpm db:migrate && pnpm db:seed`
- Install: `pnpm install`
- Dev: `docker compose up -d && pnpm dev` (web :5173, API :4000/graphql, mock destination :4100, Postgres :5432)
- Test one file: `pnpm --filter ./<package-dir> exec vitest run <path-inside-package>` ← use this while iterating
  - Example: `pnpm --filter ./services/sync-worker exec vitest run src/batch.test.ts`
- Test all: `pnpm test`
- E2E: `pnpm test:e2e` (needs Postgres up; Playwright starts the app itself)
- Lint + typecheck: `pnpm lint && pnpm typecheck`
- Format: `pnpm format`
- GraphQL codegen, after any change to the schema or to queries in `apps/web`: `pnpm codegen`
- Check that generated code is up to date: `pnpm codegen:check`
- DB migration, after any change to the Drizzle schema: `pnpm db:generate`, then `pnpm db:migrate`
- Run an installed tool with `pnpm exec <tool>`, a one-off tool with `pnpm dlx <tool>`. Not `npx`.

## Definition of done

Before finishing any change, run and pass:
1. `pnpm lint && pnpm typecheck`
2. `pnpm test` (Turborepo skips packages that didn't change)
3. `pnpm codegen:check` if you touched the GraphQL schema or queries
4. `pnpm format`
5. Bug fix: a test that fails without your fix and passes with it
6. UI change: `pnpm test:e2e`, plus before/after screenshots in the PR

## Where things live

- GraphQL is schema-first. The schema is `packages/shared/schema.graphql`; shared TypeScript types are in `packages/shared` too.
- Apps and services import shared code from `packages/*` only, never from another app or service.
- Generated code is in `apps/api/src/generated/` and `apps/web/src/gql/`. Never edit it by hand; run `pnpm codegen`.
- DB schema (Drizzle) is in `packages/db/src/schema.ts`, used by the other services. Migrations in `packages/db/drizzle/` are generated by `pnpm db:generate`, never written by hand.
- Unit tests sit next to the code: `foo.ts` → `foo.test.ts`. E2E tests are in `apps/web/e2e/`.

## Conventions

- Sync writes are batched and idempotent: every batch sent to the destination carries an idempotency key, and a retry resends the same key.
- GraphQL changes are additive. Removing or renaming a field needs approval (see Boundaries).
- Dependencies: use the latest stable version that's compatible with the rest of the stack, never a deprecated package. Check the registry (`pnpm view <package> version`) instead of relying on memory.

## Boundaries

- Always: work on a branch, run the definition of done, link the issue in the PR.
- Ask first: adding or upgrading a dependency, changing the DB schema, removing or renaming a GraphQL field, editing `.github/`, `.devcontainer/` or `pnpm-workspace.yaml`. In unattended runs (CI, headless), don't do it; explain in the PR why it's needed.
- Never:
  - push to `main` or force-push, merge or approve PRs
  - read, print or commit `.env` or any secret
  - edit generated code or hand-write migrations
  - delete, skip or weaken a failing test (no `.skip`, `.only`, or loosened assertions)
  - edit AGENTS.md, CLAUDE.md, REVIEW.md or `.claude/` unless asked
  - run `drizzle-kit push`, npm or yarn

## Git & PRs

- Branches: `<type>/<issue-number>-<slug>`, e.g. `feat/12-member-table`. Agent tools that use their own prefix (`claude/`, `copilot/`) keep it.
- Commits: Conventional Commits with the package as scope, e.g. `feat(web): add member table`.
- PRs: open as draft. Title: Conventional Commits, like a commit; it becomes the squash commit on `main`. Description: what changed, why, how you tested it, and `Closes #<issue>`.
